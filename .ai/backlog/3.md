# Epic: Distribution & Hardening + MCP Tool Support (Current)

## Summary

Distribution, hardening, and operational concerns — plus the deferred
Epic 2 items (per-session multi-LLM, ACP v2, persistence) — and **MCP tool
support**: acps gains an MCP **client** that connects to external MCP servers
(stdio transport) and exposes their tools to the model through the existing
ACP tool flow (agent-side execution, client permission grants).

The MCP client is implemented as a generic, protocol-agnostic module
(`src/mcp_client/`, Zig module `mcp_client`) — MCP is a standalone protocol
unrelated to ACP except for shared JSON-RPC 2.0 framing — so it is usable on
its own now and extractable to a separate repository later. MCP *resources*
and *prompts* client methods are trivial (same request/response pattern) and
implemented in the module; their ACP-side wiring lands with ACP v2 (whose
schema includes MCP capabilities).

## Features

### Feature: MCP client module (P1 — FIRST)
- **Use cases:** acps connects to external MCP servers and calls their tools on behalf of the ACP client; the module is reusable standalone (extractable to its own package later without a rewrite)
- **Requirements:** `src/mcp_client/` — generic MCP **client** (stdio subprocess transport: spawn, JSON-RPC 2.0 over stdin/stdout reusing `src/protocol/json_rpc.zig` framing); `initialize` handshake (MCP `protocolVersion` negotiation + capabilities), `notifications/initialized`, `ping`, `tools/list`, `tools/call`; `resources/list` + `resources/read`, `prompts/list` + `prompts/get` (same pattern — include if trivial); per-server lifecycle (connect, disconnect); MCP error mapping; exposed as Zig module `mcp_client` (`b.addModule("mcp_client", …)` in build.zig)
- **Dependencies:** `protocol/json_rpc.zig` (existing), subprocess spawning (`Io.Child`/`std.process`)
- **Verification:** transcript tests against a mock/echo MCP server (initialize → tools/list → tools/call); stdio framing tests; stdio subprocess lifecycle tests (spawn/EOF/exit)
- **Tasks:**
  - [x] `feature/mcp-client-module` — `src/mcp_client/` + `b.addModule("mcp_client", …)` + mock-server transcript tests (done — merged 686b85c)

### Feature: MCP server configuration (P1)
- **Use cases:** declare MCP servers in `config.json` without code changes
- **Requirements:** `mcpServers` section per MCP convention — `{ "name": { "command": "…", "args": […], "env": {…} } }` (stdio only for the first cut; streamable-HTTP deferred); startup validation (unknown/duplicate names, missing command, bad env); graceful startup errors naming the offending server
- **Dependencies:** MCP client module; `src/config.zig`
- **Verification:** config fixture tests; startup validation errors; selection/dispatch tests
- **Tasks:**
  - [ ] `feature/mcp-config` — `mcpServers` config section + validation (backlog)

### Feature: MCP tools in the ACP tool flow (P1)
- **Use cases:** the model can call MCP-hosted tools through the full ACP flow — the ACP client sees the tool definitions, grants permission via the existing handshake, and acps executes the call against the owning MCP server
- **Requirements:** dynamic tool entries sourced from each server's `tools/list` (MCP `inputSchema` is JSON Schema → maps directly onto the existing `Tool.parameters` shape); merged into the provider `tools` arrays alongside the static registry (`src/tools/registry.zig`); `tools/call` dispatched to the owning server on execute; rides the existing `session/request_permission` + `session/update` progress/result flow (agent-side execution); server lifecycle hooked to startup (connect declared servers; lazy connect on first use acceptable)
- **Dependencies:** MCP client module, MCP config
- **Verification:** end-to-end transcript (initialize → session/new → prompt triggering an MCP tool → permission → tool result fed back to the model); live smoke test against a real MCP server (e.g. the reference filesystem server)
- **Tasks:**
  - [ ] `feature/mcp-tools-in-acp` — dynamic registry entries + provider merge + MCP dispatch (backlog)
